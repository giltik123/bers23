# Android / Trusted Web Activity release

## Decision and boundaries

BERS ships to Android as a **Trusted Web Activity (TWA)** using
`com.google.androidbrowserhelper:androidbrowserhelper:2.7.4`. The Android package
opens the production BERS HTTPS origin in a TWA-capable browser. It does not
bundle the React application in a WebView and does not add Capacitor, a native
API proxy, a second session store, bearer-token storage, wildcard CORS or a
`SameSite=None` compatibility path.

This is intentional: browser and Android use the same deployed frontend, the
same first-party `/api/core` gateway, and the same canonical PostgreSQL/Core
authorities. Existing Secure, HttpOnly, SameSite=Strict cookies and session-bound
CSRF remain unchanged. Android Browser Helper can fall back to a normal Custom
Tab when Digital Asset Links verification or TWA support is unavailable; that
fallback is not trusted-TWA acceptance.

The Android package requires network access to the deployed product. It does
not make the browser/WASM/local-AI feature set a physical-device capability
claim. Browser support and resource limits still need device-specific testing.

## Fixed build baseline

- JDK 17.
- Gradle 8.13 (the CI workflow installs this version; no unreviewed major Gradle
  migration is implied).
- Android Gradle Plugin 8.13.2.
- Android SDK platform 36; `compileSdk 36` and `targetSdk 36`.
- Minimum Android API 24.
- Android Browser Helper 2.7.4.

Google Play's current ordinary phone/tablet requirement is target API 36 or
higher for new apps and updates. Recheck the official policy before a future
submission: <https://developer.android.com/google/play/requirements/target-sdk>.
TWA behavior and Digital Asset Links are documented at
<https://developer.android.com/develop/ui/views/layout/webapps/trusted-web-activities>.

## Prerequisites that cannot be generated by the repository

1. A real public BERS HTTPS origin, serving the frontend and first-party Core
   gateway according to `SECURITY_CONFIGURATION.md`.
2. A permanent reverse-domain Android application id.
3. A Google Play Developer account and Play Console application.
4. An upload keystore protected outside GitHub. Keep an offline backup and use a
   secret manager for automation; losing the upload key can block updates.
5. The public SHA-256 certificate fingerprint of the **Play app-signing key**.
   For pre-Play/internal testing, the local upload/debug fingerprint can be
   included too. Play Console exposes the production fingerprint under the app
   signing setup. Do not confuse it with the upload-key fingerprint.
6. Final store listing, screenshots, privacy policy, Data safety declarations,
   content rating and other Play Console metadata.

No keystore, password, OAuth secret, database credential or private certificate
material belongs in Git, CI logs, the frontend bundle or chat.

## Public release configuration

Set values appropriate to the actual product. The examples below are placeholders
and deliberately fail the release preflight if copied unchanged.

```sh
export BERS_ANDROID_URL='https://app.example.com'
export BERS_ANDROID_APPLICATION_ID='com.example.bers'
export BERS_ANDROID_VERSION_CODE='1'
export BERS_ANDROID_VERSION_NAME='1.0.0'
export BERS_ANDROID_SHA256_FINGERPRINTS='AA:BB:CC:DD:EE:FF:00:11:22:33:44:55:66:77:88:99:AA:BB:CC:DD:EE:FF:00:11:22:33:44:55:66:77:88:99'
```

`BERS_ANDROID_URL` must be exactly one public HTTPS origin: no path, query,
fragment, credentials or non-default port. It must be the same first-party web
origin whose Auth cookies and CSP are already valid. Fingerprints are public
identifiers, not passwords. Multiple fingerprints may be comma-separated, for
example the Play app-signing certificate and an internal-testing certificate.

`versionCode` must increase monotonically for every Play upload. `versionName`
is the user-facing semantic version. The debug/CI defaults are intentionally
non-release values (`app.bers.example`, `https://app.bers.example`, `0.0.0`).

Run the non-secret preflight before producing a release:

```sh
node scripts/check-android-release.mjs
```

## Build a signed Play App Bundle and matching web deployment

Use Node.js 22 or 24 for the web production build. From the repository root:

```sh
npm ci
npm run build
npm run check:browser-bundle
node scripts/check-android-release.mjs
```

Provide signing material through the process environment, not Gradle files or
command-line arguments. One interactive pattern that avoids putting passwords
in shell history is:

```sh
export BERS_ANDROID_KEYSTORE_PATH='/absolute/secure/path/bers-upload.jks'
export BERS_ANDROID_KEY_ALIAS='bers-upload'
read -rsp 'Keystore password: ' BERS_ANDROID_KEYSTORE_PASSWORD; echo; export BERS_ANDROID_KEYSTORE_PASSWORD
read -rsp 'Key password: ' BERS_ANDROID_KEY_PASSWORD; echo; export BERS_ANDROID_KEY_PASSWORD
```

Then build:

```sh
gradle -p android --no-daemon clean bundleRelease
node scripts/render-android-assetlinks.mjs
```

Outputs:

- `android/app/build/outputs/bundle/release/app-release.aab` — signed upload
  artifact when the four signing variables and real public configuration were
  supplied. Direct `bundleRelease`/`assembleRelease` fails closed on placeholder
  configuration, missing signing variables or a missing keystore.
- `dist/.well-known/assetlinks.json` — public Digital Asset Links statement
  generated from the same application id and fingerprint configuration.

Deploy the complete `dist` tree, including the hidden `.well-known` directory,
to `BERS_ANDROID_URL`. The file must be available without authentication at
`/.well-known/assetlinks.json`, with a JSON content type and no redirect to a
 different origin. Rebuilding the web frontend after generating the file may
clean `dist`; generate it after the final web build and deploy both together.

The AAB and web deployment form one release candidate. Record the exact Git SHA,
Android version code/name, application id, public origin, public certificate
fingerprints and SHA-256 of the AAB in the release evidence. Do not record
passwords or private key material.

## Debug and CI evidence

The `Android TWA` workflow runs the Node release-contract tests, Android lint
and `assembleDebug` on the exact candidate SHA. It uploads only a short-lived
`bers-twa-debug-apk` artifact. That artifact is for build/CI inspection, is not a
Play release, and does not prove Digital Asset Links, Auth, UI journeys or
physical-device behavior.

For a local debug build with the checked-in placeholder configuration:

```sh
gradle -p android --no-daemon lintDebug assembleDebug
```

A placeholder build normally opens a Custom Tab rather than a verified TWA.
Use a real test origin and a matching fingerprint for functional testing.

## Required candidate verification

Hosted green CI is necessary but not sufficient. Before submission:

1. Verify the exact candidate SHA has passed `BERS Required Acceptance`, Auth
   Lifecycle Browser E2E, Node builds, real PostgreSQL suites, production image,
   production dependency audit and Android TWA checks.
2. Fetch the deployed asset-links URL and validate its JSON, package name and
   fingerprints. Confirm no redirect or accidental HTML response.
3. Install the signed candidate through the intended Play internal-test track.
   A debug APK is not equivalent.
4. On physical Android devices, verify cold launch and that successful Digital
   Asset Links verification hides the browser URL bar. Test at least one
   Android 16/API 36 device and the oldest supported device class practical.
5. Complete registration, email verification, login, logout, session restore
   after process death, password recovery and Google OAuth. Verify no session
   token appears in Android files, logs, URLs or JavaScript storage.
6. Create/rename/archive/delete a Project, upload an original, reload after
   process death, and confirm canonical server persistence and error recovery.
7. Exercise the Editor and Fashion journeys intended for this release, including
   uploads, final export/download, rotation, resizing, keyboard, Back behavior,
   deep links, offline recovery, RU/EN localization and TalkBack/keyboard focus.
8. Confirm the wrapper requests no dangerous Android permission. Browser-owned
   camera/file/location prompts must still follow the web product's consent UX.
9. Complete Play Console policy, privacy, Data safety, content rating and store
   listing review. Resolve every pre-launch report finding rather than treating
   a successful upload as release acceptance.

Do not claim production Android readiness until these external checks have
actual evidence tied to the release SHA. No physical-device, Play Console or
production deployment evidence is generated by this repository change alone.

## Rollback and limitations

- Roll back the web deployment and its asset-links file together when changing
  the Android association. Keep the previous association until the replacement
  is verified to avoid breaking installed TWAs.
- Use Play Console's release halt/rollback controls for a bad Android wrapper;
  web fixes still require the normal reviewed web deployment process.
- This contour has no bundled offline editor, native push notification, native
  share target or Play Billing integration. Those are separate product tracks,
  not capabilities to infer from the presence of an Android package.
